Talk 1 · Quality Engineering

No time to test: can AI write the acceptance test for the people who must sign it off?

Marck Petersen · Quality Engineering & Citizen Development

Every system upgrade ends the same way. Before anything reaches production, the real users must test it in User Acceptance Testing (UAT) and approve it. But the key users who own that approval rarely have time to write test cases and scenarios, so UAT gets squeezed, delayed or reduced to a quick click-through. In this talk we look at that last step of the V-model and ask a practical question: can AI read the requirements and prepare test scenarios that a busy user only needs to review, run and sign? To make the problem concrete, we use a small Airport Stand Allocation Simulator that stands in for a real system going through change.

Talk 2 · Artificial Intelligence

From requirement to test case: what happens inside the language model, and where it fails

Speaker to be confirmed · AI specialist

Large language models can produce dozens of test cases from a single requirement in seconds. But are they testing the system or repeating the text back to us? This talk opens the box. We look at how a model turns a business rule into concrete steps and expected results, why it sometimes invents rules that do not exist, and how techniques such as structured prompts, examples and retrieval of the real requirements make the output more reliable. We finish with a simple way to measure whether AI-generated tests actually cover the rules that matter.

The situation

A changed system has to be approved by people who have no time

An existing system is upgraded, or new features are added. The developers have done their unit, integration and system testing. Before the change can go to production, the business must confirm in a test environment that the system still does what they need. That last step is User Acceptance Testing.

UAT is done by real users: planners, operators, case handlers. They know the business best, and they are the ones who sign the approval. They also have full-time jobs. Preparing test cases, test scenarios and test data is work they rarely have time for.

This is not one organisation's problem. It appears wherever an existing production system is upgraded or a new one is introduced.

What usually happens

  • Test preparation starts late, or not at all
  • Users test what they remember, not what changed
  • Business rules go untested because nobody wrote them down as tests
  • Sign-off is given on trust, or go-live is delayed

Where we are in the project

The last step on the right side of the V

Each test level on the right validates a design level on the left. Acceptance testing checks the system against the original requirements, and it is where the users decide whether the system goes to production.

The problem to solve

Go-live is fixed. The time to prepare the test is not there.

How can we use AI so that UAT scenarios are still prepared, executed and documented, even when the key users have no time to write them?

On paper, the project plan has a clear slot for acceptance test preparation. In practice, development and system testing run late, while the go-live date stays where it is. The time that disappears is the time the key users needed to prepare.

The key users are also the only people who know which business situations really matter. Nobody else can approve the system for them, and they cannot step away from their daily work for weeks to write test material.

What test preparation asks of a key user

  1. Understand what has changed in this release
  2. Choose the business situations that must still work
  3. Write each one as steps with expected results
  4. Find or create test data that triggers each situation
  5. Plan how results are recorded as evidence for sign-off

What happens when it is skipped

  • Testing becomes a quick click-through of familiar screens
  • Changed business rules are never checked on purpose
  • There is no record of what was tested
  • Approval is given on trust, or go-live slips

System under test

Airport Stand Allocation Simulator

The simulator stands in for a real problem: a business system in production that is being changed and must pass user acceptance testing before go-live. Aircraft land, and the system assigns each one a parking stand based on wingspan, following clear business rules. For this event, the simulator is the system under test (SUT).

Four stands

A1≤ 24 m
A2≤ 36 m
A3≤ 52 m
A4≤ 70 m

Plus a ground waiting area with room for 3 aircraft. Each planned scenario cycle runs for about two minutes and repeats.
